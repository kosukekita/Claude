# パイプライン仕様

順序は `workflow.js` が保持する。**統括役の記憶ではなくスクリプトが順序を持つ**ので、
文脈が圧縮されてもステップは落ちない（これが参照元 hyperresearch の最大の失敗モードだった。
1200行の単一スキルが実行中に文脈から追い出され、統括役が黙って工程を飛ばし、
複数ドラフトを1本に置き換えて、成績の落ちたレポートを出した — 再読しなかった実行の100%で発生）。

## 担当エージェント

| エージェント | ツール | 役割 |
|---|---|---|
| `dr-planner` | Read/Write/Grep/Glob（**ネットワーク無し**） | 分解・tier分類・3レンズ探索計画・対立クラスタ・証拠ダイジェスト |
| `dr-fetcher` | Read/Write/Bash/Grep/Glob/WebFetch/WebSearch | 割当URLの取得・ノート化・逐語引用つきクレーム抽出・一次資料追跡 |
| `dr-depth-investigator` | 同上 | 争点1つを担当し、コミットした立場を書く |
| `dr-drafter` | Read/Write/Bash/Grep/Glob | 割り当てられた切り口でドラフト1本 |
| `dr-synthesizer` | Read/Write/Bash/Grep/Glob | 複数ドラフトから最終稿を1回だけ書く（**統合専任**） |
| `dr-critic` | Read/Write/Grep/Glob（**Edit・Bash なし**） | 1観点から攻撃し、指摘を書く |
| `dr-patcher` | **Read/Edit のみ** | 指摘を外科的差分として当てる |
| `dr-cite-checker` | Read/Grep/Glob/Write（**Edit・Bash なし**） | (文,引用) の結合を懐疑的に判定 |
| `dr-runner` | **Bash/Read のみ** | コマンドを1回実行し stdout/stderr/終了コードをそのまま返す |

ツールの割り当ては仕様であって好みではない。`dr-critic` から Edit を、
`dr-patcher` から Write を外しているのは、**指示では守られなかったから**。

**Bash も外している**のが要点。`Edit` だけ取り上げても `Bash` が残っていれば
シェル経由でレポートを書き換えられるので、「批評者はレポートを変更できない」という
性質が成立しない。ロックは、迂回路を全部塞いで初めてロックになる。
`dr-critic` / `dr-cite-checker` は `Grep` / `Glob` / `Read` で vault を調べられるので
`Bash` は不要（探索能力は落ちない）。

## 機械的な検査を、なぜエージェント経由で走らせるのか

ワークフローの実行環境にはプロセス起動もファイルシステムも無い。
なので `shipgate.py` のようなスクリプトを走らせるには、どうしてもエージェントを1枚挟む必要がある。

そこで `dr-runner` は「コマンドを1回実行して stdout / stderr / 終了コードを**そのまま返す**」
だけの契約にし（解釈・要約・再実行を全部禁止）、**合否の判定はワークフロー側の JS が行う。**
判定ロジックをプロンプトに書かない。エージェントは配管であって審判ではない。

これに伴う設計上の制約が1つある。**stdout に大きな出力を出さないこと。**
返り値をエージェントが構造化フィールドへ書き写す以上、
数百KBの出力は破綻する。**集計とパスだけを stdout に出し、中身はファイルで受け渡す。**

## フェーズ

### F1 決定
質問を原子項目・必須見出し・応答形式に分解し、tier を決める。ユーザーの原文を1文字も変えずに保存する。

- **受け入れ**: 保存された原文が入力と完全一致すること。以降の全サブエージェントのプロンプトに逐語で入ること。
- **なぜ**: 質問は多段のサブエージェントを通るうちに言い換えられて痩せる。逐語で運ぶ以外に防ぐ方法がない。
- **なぜ必須見出しか**: 事実が全部揃っていても、ユーザーの聞き方（対象ごと／時系列）ではなく
  自分の分析軸で組み替えたレポートは評価が落ちる。**指示遵守はばらつきが最大の失点**。

### F2 探索計画（3レンズ）
原子項目ごとに、3つのレンズで検索を計画する。

| レンズ | 探すもの |
|---|---|
| 網羅 | 各項目の中核的事実・直近の動向・登場する固有名詞 |
| 引用チェーン | 学術APIで正典・原論文・二次記事が依拠している一次資料 |
| **敵対的** | 「〜の批判」「〜の限界」「〜がうまくいかない理由」「対立する枠組み」 |

- **受け入れ**: 3レンズすべてが計画に存在し、敵対的検索が下限を満たし、
  カバレッジ行列の全行に対応する検索があること。**足りなければ停止**（警告では通さない）。
- **なぜ**: 場当たりの検索は同じ3つの小論点にソースを40件積む。
  敵対レンズが無いと、**形成されつつある結論に対する最強の反論が corpus に入らない**。

### F3 収集
学術APIを web 検索より先に叩く。取得前に vault を検索する。URLに効用スコアを付け、
重複を除き、**重なりゼロ**のバッチに分けて `dr-fetcher` を並列起動する。

- **受け入れ**: バッチが重複しないこと。fetcher が自分のバッチ外を検索しないこと。
  各ノートに**逐語引用つき**クレームが書かれること。引用のないクレームは不採用として数える。
  Wikipedia は出典ハブとしてのみ使い、引用元にしない。
- **なぜ vault 先読みか**: 同じものを2度取らない。セッションを重ねるほど速く厚くなる唯一の仕組み。
- **なぜ逐語引用が必須か**: 引用のないクレームは下流（証拠ダイジェスト・引用検証）で
  照合できず、実質的に存在しないのと同じになる。
- **なぜ一次資料追跡か**: 二次記事は数値を丸め、方法の限界を落とす。
  追跡を省いた収集は「他人の要約の集合」にしかならない。

### F4 カバレッジ検査
原子項目ごとにソース数を数え、薄い／未被覆の行に第2波を撃つ。

- **受け入れ**: 0件のまま残った項目が、黙って消えずレポートまで運ばれること。
- **なぜ**: 範囲が静かに狭まる事故（「SaaS全般」→「決済SaaS」）は、
  検索の欠落→ソースの欠落→節の欠落と連鎖する。最も安く捕まえられるのがここ。

### F5 独立性・品質・撤回
URL正規化／ワイヤー署名／本文類似度の3経路でクラスタを作り、代表以外の独立性を下げる。
撤回を洗い、品質を床値にする。

- **受け入れ**: 「独立ソース○件が一致」の判定が、**件数ではなく独立性の和**で行われること。
- **なぜ**: 1本のプレスリリースの5転載は、5つの一致ではなく1つの声。
  数えるだけだと合意が水増しされ、確信が実態より高く出る。
- **実測**: ワイヤー記事の4転載 → 独立性の和 1.75。

### F6 対立グラフ（deep のみ）
ソース間の実質的な矛盾をクラスタにまとめる。

- **なぜ深掘りより先か**: 争点を「面白そうだから」で選ぶと、証拠が割れていない所を掘ることになる。
  **証拠が実際に分岐している場所**を先に特定してから掘る。

### F7 深掘り（deep のみ）
争点ごとに `dr-depth-investigator` を並列起動する。

- **受け入れ**: 各中間ノートが「コミットした立場」と「何が分かれば変わるか」を持つこと。
  記述だけのノートは不良として再実行。
- **なぜ**: **ヘッジは伝播する。** 中間ノートがヘッジすると、ドラフトも統合も批評もヘッジし、
  「いろいろな見方があります」で終わる報告書が出る。
- 「何が分かれば変わるか」は、統合時に**どこが議論の弱点か**を教える欄でもある。

### F8 証拠ダイジェスト
逐語引用つきの主要クレーム索引を作る。ドラフト担当が直接読む一次材料になる。

### F9 ドラフト
`standard` は1本、`deep` は3本を**別々の切り口**で並列作成する。
必読ノートは統括役が切り口ごとに用意する。

- **なぜ切り口を指定するか**: 書き手に読むものを選ばせると、3本とも同じ論法に収束して、
  統合する意味が消える。
- **なぜ必読ノートを全文読ませるか**: 要約から書くと出てくるのは言い換えであって統合ではない。

### F10 統合（deep のみ）
`dr-synthesizer` が3本から最終稿を**1回だけ**書く。

- **なぜ統括役が書かないか**: ここまで長時間走った統括役の文脈は実行管理のログで埋まっている。
  その状態で書かれたレポートは質が落ちる（パッチ担当と推敲担当を別エージェントにして
  安定したのと同じ理由）。
- **なぜ計画とアウトラインを先に渡すか**: 計画なしの統合は、元の3本より薄いものを生む。

### F11 批評
`dr-critic` を4観点（反証／深さ／網羅／指示遵守）で並列起動する。**批評は編集しない。**

- **受け入れ**: 各批評の件数に上限。原文クエリを**ドラフトより先に**読むこと。
- **なぜ上限か**: 細かい指摘を40件返すと重大な指摘がその中に埋もれ、実際には読まれない。
- **なぜクエリを先に読ませるか**: ドラフトを先に読んだ批評者は、ドラフトの枠組みを引き継ぎ、
  その盲点をそのまま盲点にする。

### F12 パッチ
`dr-patcher`（Read/Edit のみ）が指摘を外科的差分として当てる。**パッチログは事前に作っておく**
（Edit は新規ファイルを作れないため、無いと書き込み先を失って報告に紛れ込み、取りこぼす）。

- **受け入れ**: 最上位の重要度の指摘が、適用されるか明示的に上申されるかのどちらかであること。
- **なぜ再生成禁止か**: 書き直しは、批評が問題にしていない箇所の検証済みの記述まで作り直す。
  引用の逐語性・数値・出典の結合が静かに壊れる。

### F13 cite-check
`citecheck.py` が (文, 引用) を抽出し機械的にトリアージする。
クレームの逐語引用が文に現れる、または文中の**すべての**数値が引用先クレームに含まれるなら自動通過。
残りだけを `dr-cite-checker` が判定し、第2のパッチを当てる。

- **受け入れ**: 標本抽出が決定的であること（乱数禁止・resume で同じ標本）。
  どのノートにも解決しない引用は最重要の指摘。
- **なぜ数値は全部一致が要るか**: 1文に数値が2つあり出典が片方しか支持しない、
  という失敗が実在する。「概ね合っている」で通すと捕まらない。
- **なぜパッチの後か**: パッチは文と引用を動かす。**実際に出荷される文**を検証する必要がある。

### F14 出荷ゲート
`shipgate.py` を**1コマンド**で実行し、終了コードが判定になる。

検査項目: レポートの存在／必須見出しが順序どおり／語数が範囲内／引用密度が下限以上／
**引用符で囲まれた全スパンが vault ノートに逐語で存在する**／撤回ソースを無断引用していない／
cite-check の重大指摘が解決済み。

- **受け入れ**: 失敗したらレポートを直して再実行。規定回数で通らなければ `blocked` として
  正直に報告して終わる。
- **なぜ1コマンドか**: 検査を分けると、モデルは失敗を「誤検知」と再解釈して出荷する。
  実測で、幻覚引用24件がそうやって出荷された。**論じる継ぎ目を作らない。**
- **実測**: 幻覚引用のレポート → exit 1。撤回ソース無断引用 → exit 1。正常なレポート → exit 0。

## 検査が保証しないこと

検査が見るのは**構造と結合**であって、事実の正しさではない。
「引用符の中身が出典に逐語で存在する」ことは検証できるが、
「その出典が正しい」ことは検証できない。そこは人間の担当。
