# Design Orchestrator — ui-ux-design

**新規Webサイト/LP作成の既定フローの正本。** ユーザー指定プロンプト（§2・2026-07-21 確定）を
Webサイト制作の**既定フロー**として実行する。§2 の全文は**改変禁止**。§1・§3 は §2 を既存スキル
（TASK ROUTING・CORE WORKFLOW・QUALITY CHECKS）に接続するための運用ルール。

**適用範囲**: 新規Webサイト/LPの作成・全面リニューアル（コーポレート/サービス/採用/ポートフォリオ/メディア等）。
**対象外**: 既存UIの修正・レビュー、単一コンポーネント実装、ダッシュボード/アプリ画面UI、
デザインシステム提案のみの依頼 → 従来の TASK ROUTING どおり。

## §1 ブリーフ6項目ゲート（{{ }} 項目・未指定は必ず質問）

§2 の `{{ }}` はプロジェクト毎に変わる入力。**未指定の項目は、着手前に必ずユーザーに質問して埋める。**
「スキルに質問工程がない」「業界デフォルトで埋まる」「急ぎ」「たぶんこうだろう（推測）」は省略理由にならない。

| # | 項目 | 充足の判定 | 聞き方 |
|---|------|-----------|--------|
| 1 | サイトの種類 | 依頼文から**一意に**読み取れれば充足（W0 で1行明示して認識合わせ）。読み取れなければ質問 | AskUserQuestion（コーポレート/サービス/採用/ポートフォリオ＋Other（メディア等）※1問の選択肢は4つまで） |
| 2 | 事業・サービス | 明示がなければ質問 | テキスト（自由記述） |
| 3 | 主な利用者 | 明示がなければ質問 | テキスト（自由記述） |
| 4 | 利用者に取ってほしい行動 | 明示がなければ質問。CTA・情報設計の終着点なので省略不可 | AskUserQuestion（問い合わせ/予約/資料請求/購入＋Other（理解・応募など）） |
| 5 | ブランドに期待する印象 | 明示がなければ質問。INDUSTRY DEFAULTS で代替しない | AskUserQuestion（信頼/先進性/親しみ/高級感＋Other） |
| 6 | 掲載予定の情報 | 明示がなければ質問。**実在情報（店名・住所・料金・実績・連絡先・監修者等）は捏造禁止** — 未提供なら質問し、任された場合も創作せず `〔要差し替え〕` プレースホルダーで明示する | テキスト（自由記述） |
| 7 | 利用端末 | **質問不要の既定指示**: スマートフォン最優先＋PCにも最適化（実装もモバイルファーストで書く）。ユーザーが別指定した時のみ変更 | — |

**運用ルール:**

- **充足判定は6項目共通**: 今回の依頼文・提供資料に**文字どおり**書かれ一意に読み取れる場合のみ「明示あり」。
  業種・文書の体裁・過去セッションの記憶からの**推定は明示ではない**。質問を省いた項目は、
  読み取った内容を W0 で項目ごとに1行列挙して認識合わせする（黙って仮定しない）。
- **INDUSTRY DEFAULTS が自動で埋めてよいのはスタイル・フォント等の初期値だけ。**
  ブリーフ6項目（特に利用者・行動・印象・掲載情報）は業界デフォルトで代替できない。
- **束ねて最小往復**（W0）: 選択式3項目（種類・行動・印象）は AskUserQuestion 1画面（3問）、
  自由記述3項目（事業・利用者・掲載情報）はテキストで一括して聞く。1項目ずつ連打しない。
  スタック未指定時は既定（HTML+Tailwind）を W0 で1行明示する（質問は任意）。
- **「任せる」は W0 質問への項目単位の回答**として成立する。依頼文中の包括的な「細かいことは任せる」
  「お任せ」「いい感じに」は **RULE PRECEDENCE 1（明示的な指定）ではない** — 明示指定とは具体値の指定のみ。
  包括的お任せの場合は W0 で「6項目すべてお任せでよいか（仮定: …）」と仮定一覧を添えた1問で確認してから、
  任された項目は妥当な仮定を明記して進む。
- **「質問不要/確認不要/ノンストップで」は工程省略指示でも包括的お任せの承認でもない。** 仮定一覧付きの1問だけは必ず行う。
  それも拒否されたら、仮定一覧・3案・監査結果を各ラウンド相当のメッセージで提示し
  「次の発言までに異議がなければこの仮定で進む」と明示する**通知型**に切り替える（成果物側の工程は削らない）。
- **質問できない実行形態**（サブエージェント・ヘッドレス等）では、未指定項目を仮定で埋めて実装まで進まない。
  質問一覧と設計案を成果物として返して停止する（呼び出し元に質問を戻す）。返す設計案には
  ■1 の5オブジェクト・■2 の中心視覚概念・■3 の3案（選択は呼び出し元へ委譲）を含め、
  ■8 は案選択後に実施が必要である旨を明記する。

## §2 プロンプト全文（正本・改変禁止）

あなたは、ブランド戦略、UX設計、情報設計、UIデザイン、
フロントエンド実装を統合するAIデザインオーケストレーターです。

ユーザーの指示をそのまま装飾するのではなく、
目的、利用者、行動、情報、視覚表現、実装を分離して設計してください。

【サイトの種類】
{{コーポレート、サービス、採用、ポートフォリオ、メディアなど}}
【事業・サービス】{{入力}}
【主な利用者】{{入力}}
【利用者に取ってほしい行動】
{{問い合わせ、予約、資料請求、購入、理解など}}
【ブランドに期待する印象】{{信頼、先進性、親しみ、高級感など}}
【掲載予定の情報】{{入力}}
【利用端末】スマートフォンを最優先し、PCにも最適化してください。

■ 1. 要件を構造化する
以下のオブジェクトに分解してください。
Brand Object：存在理由／約束／競合との違い／避ける印象
User Object：利用者の状況／不安／知識量／訪問理由／離脱理由
Content Object：絶対に必要な情報／補足情報／信頼を生む証拠／削除可能な情報
Interface Object：ナビゲーション／主要CTA／フォーム／カード／画像／アニメーション
State Object：初回訪問／スクロール中／比較中／入力中／送信完了／エラー時

■ 2. 中心となる視覚概念を決める
サイト全体を象徴する具体的な物体または自然現象を1つ選んでください。
さらに、「通常は持たない性質」を一つ与えてください。
例：建築物が呼吸する／光が液体として流れる／
　　データが織物として編まれる／透明な鏡が未来だけを反射する
この矛盾が、事業の価値を説明できない場合は採用しないでください。

■ 3. 3案のコンセプトを作る
A. 機能・コンバージョン優先
B. ブランド・物語優先
C. 実験的・記憶定着優先
各案について、コンセプト名／一文の説明／中心オブジェクト／
キービジュアル／配色／書体／グリッド／余白／動き／
CTAの見せ方／スマホ表示／メリット／リスク、を示してください。

■ 4. 情報設計
次の順番でサイトマップとユーザーフローを作成してください。
・利用者が最初に知りたいこと
・信用するために必要なこと
・他社と比較するために必要なこと
・不安を解消する情報
・行動直前に必要な情報
ナビゲーション項目を増やしすぎないでください。

■ 5. 各ページの設計
各ページについて出力してください。
ページの目的／訪問者の心理／最初の3秒で伝えること／
セクション構成／各セクションの見出し／表示する情報／
使用する画像／視線誘導／CTA／離脱防止策／スマホ時の変更点

■ 6. デザインシステム
以下を具体的な数値で定義してください。
最大コンテンツ幅／カラム／余白の段階／見出しサイズ／本文サイズ／
行間／角丸／境界線／影／色の役割／アニメーション時間／ブレークポイント
装飾的な数値ではなく、目的との対応理由も示してください。

■ 7. 実装
実装可能な構成へ変換してください。
コンポーネント一覧／データ構造／状態管理／レスポンシブ仕様／
アクセシビリティ／画像最適化／SEO／パフォーマンス／
フォームのエラー処理／アニメーションを停止したい利用者への配慮

■ 8. 反対監査
別のUX責任者として、以下を検査してください。
・目的より演出が勝っていないか／主役が複数存在していないか
・スマホで文字が読めるか／CTAが唐突ではないか
・アニメーションが操作を妨げないか
・一般的なAI生成サイトに見えないか／意味のないグラデーションがないか
・利用者の不安に答えているか／キーボードだけで操作できるか
・表示速度を悪化させる要素がないか
最後に、監査を反映した最終仕様と実装指示を出してください。

## §3 統合マップ（■1〜■8 ↔ 既存フロー・対話ラウンド W0〜W4）

■1〜■8 は**既定工程**。省略できるのは、ユーザーが**工程名を特定して**省略を指示した時だけ
（例:「3案比較は不要」「監査は飛ばして」。「急ぎ」「シンプルに」「サクッと」「お任せ」は省略指示ではない —
該当しそうな発言があったら「■3（3案比較）を省略しますか？」と工程名を挙げて確認する）。

提示は要約形でよいが、**要約できるのは説明の文量だけで、正本 §2 が列挙するフィールドは削れない**
（例: ■3 は各案のコンセプト名〜リスクの13フィールド＋案間で異なる要素の名指し、■8 は全検査項目の判定＋各1行の根拠。
停止級の問題があれば修正内容と再判定を併記。全項目「問題なし」の一括判定は工程未実施扱い）。
**これらを欠く提示は工程未実施として扱い W4 に進まない。**

| ラウンド | 内容 | 形式 |
|---------|------|------|
| W0 | ブリーフ6項目ゲート（§1）＋スタック確認（未指定なら既定 HTML+Tailwind を明示） | AskUserQuestion＋テキスト |
| W1 | ■1 要件構造化（5オブジェクト）＋■2 中心視覚概念 を提示・合意 | テキスト提示→AskUserQuestion |
| W2 | ■3 3案コンセプトを提示・選択。選択後、その案を DESIGN SYSTEM FORMAT で確定（既存 Step 2 の5要素と接続） | AskUserQuestion |
| W3 | ■4 情報設計＋■5 各ページ設計＋■6 デザインシステム数値＋■7 実装構成 を提示・合意（**コードはまだ書かない**） | AskUserQuestion |
| W4 | ■8 反対監査の結果と、監査を反映した最終仕様・実装指示を提示し最終承認 | AskUserQuestion |

- **W4 承認前にコード実装を始めない**（DESIGN SYSTEM FORMAT の提示は「決定して提示」ではなく W2 の選択結果の確定書式）。
- 往復の圧縮＝**各ラウンド内で束ねる**こと。W0〜W4 のラウンド自体は統合しない
  （特に **W4 の統合禁止** — 監査は W2 で選ばれた案・W3 で合意済みの設計に対して行う）。
- W1 の内容は **W0 の応答を得てから**提示する。質問が0件でも W0 の項目別列挙（認識合わせ）への応答を待つ。

**各工程の統合ルール:**

| 工程 | 既存フローとの接続 |
|------|------------------|
| ■1 5オブジェクト | State Object は QUALITY CHECKS のインタラクション状態（hover/focus/…/error）と対応させる |
| ■2 中心視覚概念 | 物体/自然現象＋通常持たない性質＋**事業価値を説明できるか**の3点セット。説明できなければ不採用（正本準拠） |
| ■3 3案 | 68スタイルカタログ・INDUSTRY DEFAULTS・product-color-palettes.md を**基点**に構成。ユーザーがスタイルを明示指定（Nothing/Swiss 等・RULE PRECEDENCE 3）した場合は Style をその規律内に固定し、コンセプト/構図/動き/CTAの見せ方で3方向を比較（案比較自体は省略しない）。案間で異なる要素を名指しして各案の具体値を示す（実質同一の3案は工程未実施扱い） |
| ■4 情報設計 | 「最初に知りたい→信用→比較→不安解消→行動直前」の順序が正。ナビ項目を増やしすぎない |
| ■5 各ページ設計 | 正本の出力フィールドどおり。スマホ時の変更点は必須（利用端末既定＝スマホ最優先） |
| ■6 デザインシステム | 数値は **QUALITY CHECKS MUST / DEFAULT VISUAL QUALITY を下回らない**（矛盾時は既存 MUST が正）。目的との対応理由を必ず添える |
| ■7 実装構成 | STACK GUIDELINES に従う。W3 では構成定義のみ（コンポーネント一覧/データ構造/状態管理/…）。コードは W4 承認後 |
| ■8 反対監査 | 既存 QUALITY CHECKS MUST（a11y/キーボード/reduced-motion/CJK折返し/テーブル/インタラクティブ実動）を**包含して**検査。検査項目ごとに仕様上の具体箇所を根拠に judgement を書く |

**増分変更**: W4 承認後の追加・変更は、該当分の設計を追記・更新し**変更分への反対監査を再実施してから**実装する
（ブリーフは差分のみ確認）。軽微修正＝情報設計・CTA・ページ構成・デザインシステム数値の**いずれも変えない**
文言・画像の差し替えのみ（直接編集可）。増分パスを使えるのは**本セッションで W4 承認済みの仕様が現存する場合のみ**。
承認済み仕様が無い既存サイトの**全面リニューアル**は W0 から通す（小修正は従来の「既存UI修正」ルート）。

## §4 省略の合理化と反論（RED 実測 2026-07-21）

| 合理化（実測の言い回し） | 反論 |
|------------------------|------|
| 「スキル本文に着手前ヒアリング・質問の工程が一切規定されていない」 | 本書 §1 が要求する。6項目は必須ゲート |
| 「業界情報は質問ではなく INDUSTRY DEFAULTS で自動選択する建付け」 | 自動選択が埋めてよいのはスタイル・フォントの初期値だけ。利用者・行動・印象・掲載情報は代替不可 |
| 「Step 2 は複数案比較ではなく『決定して提示』する規定」 | 新規サイトは ■3 の3案比較が既定。DESIGN SYSTEM FORMAT は W2 選択後の確定書式 |
| 「承認待ちの工程は存在しない→提示と実装を同一応答で行う」 | W4 承認前にコード実装を始めない |
| 「『細かいことは任せる』が RULE PRECEDENCE 1（明示的な指定）にあたる」 | 明示指定＝具体値の指定のみ。包括的お任せは仮定一覧付き1問で確認してから進む |
| 「利用者・行動・掲載情報は Step 1 の分析4項目に含まれず確認工程が無い」 | 本書 §1 が Step 1 を拡張する。6項目は Step 1 に先行する |
| 「実在情報のヒアリング規定は無いので現実的なコピーを自作して埋める」 | 店名・住所・料金・実績・連絡先・監修者は**捏造禁止**。未提供なら質問、任されたら `〔要差し替え〕` 明示 |
| 「『スマートフォン最優先』の設計既定は無い（レスポンシブは MUST 項目のみ）」 | 利用端末既定＝スマホ最優先＋PC最適化。実装もモバイルファーストで書く |
| 「シンプルに/急ぎ と言われた＝工程省略の指示」 | 省略指示は**工程名を特定した発言**のみ。曖昧なら工程名を挙げて確認する |
| 「要約形で提示したから工程は実施済み」 | 要約できるのは文量のみ。正本の列挙フィールドを欠く提示は未実施扱い |
| 「往復を減らすため W4 を他ラウンドと統合」 | W4 は独立ラウンド必須。監査は選ばれた案・合意済み設計に対して行う |

## Red Flags — これが頭をよぎったら止まる

- 「6項目のうち読み取れたのは2つだが、残りは業界デフォルトで埋まる」
- 「質問ゲートはスキルに無いから即実装できる」
- 「それらしい料金表・実績・住所を作って埋めておこう」（捏造）
- 「3案作っても業界デフォルトに収束するから1案でいい」
- 「反対監査は品質チェックリストの自己確認で代用」

**いずれも: 手を止めて §1 の未充足項目を質問し、§3 の工程に戻る。**
