# Business: Validate Before Building

## 核心原則

**「作ってから売る」の逆順で失敗する。作る前に "売れる証拠" を確認する。**

新規プロダクト相談で最も多い失敗は、需要検証を飛ばして実装計画・技術スタックの話に直行すること。エンジニアの自然な傾向がこれ。このスキルは、コードを1行も書く前に「本当に売れるのか」を確認する4つのゲートを課す。

**このスキルが止めるもの:** 「誰も欲しがらなかったものを、時間をかけて完成させる」

## いつ使うか

- ユーザーが新規アプリ/SaaS/ツール/プロダクト/事業を「作りたい・立ち上げたい・収益化したい」と言った瞬間
- 技術スタック（React, Next.js, Supabase 等）や機能が既に決まっていても**発動する**（むしろ決まっている時ほど危険＝需要未検証で実装に走りやすい）
- mvp-development / brainstorming スキルを使う**前**の意思決定ゲートとして

**使わない場面:** 純粋な学習・練習目的でアプリを作る（収益・ユーザー獲得が目的でない）と明言された時。この場合はゲートを課さず、そう確認したうえで実装支援へ進む。

## 絶対ルール（Iron Law）

**需要検証を飛ばして実装計画・技術構成・コーディングに入ってはならない。**

ユーザーが「技術スタックは決めた」「早く作りたい」「アイデアは固まってる」と言っても、まず下の原則を1つずつ確認する。技術の話・`create-next-app`・データ設計・機能一覧は、原則1〜3（土俵選びの原則1.5を含む）をユーザーと通過した**後**にしか始めない。

**原則1の市場調査（競合・需要・課金導線）は、ユーザーの手作業に丸投げせず deep-research スキルで自分で実行する。** 「調べておいてください」で終わらせない。

**「作りたい」に応えることは、実装を即開始することではない。「売れるものを作る手助け」が本当に応えること。**

## 4原則（この順で確認する）

### 原則1. 作る前に「売れる証拠」を確認する

**まず市場調査を deep-research スキルで実行する（自分で走らせる）。** 検索ボリューム・競合・課金導線は、ユーザーの手作業を待たずエージェントが調べられる。**REQUIRED SUB-SKILL:** 原則1に入ったら deep-research スキルを起動し、下の5点を調査項目にして「競合の一覧と料金・集客経路 / この課題の検索需要 / 既存の無料代替 / 想定課金額の相場」を引用付きで調べ、結果を5点フレームに整理してユーザーに返す。素の単発 WebSearch を場当たりに叩くのではなく、deep-research の fan-out 検索＋敵対的検証＋引用付き合成を使う（競合を数社の具体名・料金・精度まで、主張は裏取りして）。

調査に足りない情報（誰の・どのニッチか等）はユーザーに聞く。ただし「聞けば分かること」と「調べれば分かること（競合・相場・需要）」を混同せず、後者はまず自分で調べる。

**確認する5点:** 実装に入る前に以下をユーザーと確認する。1つでも答えられない・怪しいなら、そこが最初の宿題。

| 確認項目 | 問い | 確認手段 |
|---|---|---|
| 検索ボリューム | この課題を人は検索しているか（＝需要が言語化されているか） | Googleキーワードプランナー / Ahrefs / ラッコキーワード / 「〇〇 おすすめ」の検索数 |
| 競合の集客状況 | 既に売れている競合はいるか。彼らはどこから客を得ているか | 競合のSEO順位・広告出稿・レビュー数。**競合ゼロは「需要なし」のサインの可能性** |
| 自分も使いたいか | 作り手自身が本気で毎日使いたいか（一次情報を持てるか） | 自分がその課題の当事者か。当事者なら圧倒的に有利 |
| メンテの簡単さ | 運用が現実的か（API代・保守・スケール） | 月額運用コスト、依存API、1人で回せるか |
| お金に至る道 | 「使われる」から「課金される」までの道筋が見えるか | 誰が・いくら・なぜ払うか。無料で代替されないか |

> **なぜ大事か:** 多くの人が「作ってから売る」で失敗する。これはその逆の順番。

**「競合が既に無料でやっている」を軽視しない。** 議事録要約をZoom/Teamsが無料内蔵、のようにプラットフォーム本体が無料で提供する領域に有料で正面から挑むのは非常に苦しい。この場合は原則2（ニッチ特化＝1%改善）で勝ち筋を作る。

### 原則1.5. 「人と金が既に集まっている場所」に相乗りする（おこぼれ戦略）

> 原則1で「その課題に需要があるか」を確認したら、原則2（どう差別化するか）に入る前に「**どこで戦うか＝土俵選び**」をここで決める。原則1〜4が「市場を選んだ後」の話なのに対し、この原則だけが「そもそもどの市場を選ぶか」を扱う上流のゲート。ここを外すと、良い検証も良い差別化も、人のいない土俵で消耗する。

**やること:** ゼロから集客する前に、**既に人と金が集まっているプラットフォーム／群衆／経済圏**を1つ選び、その中で"ついでに買われる・必要とされる隣接商品"を投じる。集客コストを他人の集客にただ乗りしてゼロ化する、という市場選択そのものの原則。核心は **「自分で金を掘る」のではなく「金を掘りに来た群衆に道具を売る」** 側に回ること。人が集まる場所には、その集まりが副次的に生む需要（隣接需要）が必ず発生する。それを先取りして供給する。

- **群衆ドリブンで市場を選ぶ:** 「良いアイデアだから人を集める」の逆。「既に人が集まっている → そこで何がついでに売れるか」の順で発想する
- **ただ乗りできる集客資産を特定する:** 自分の広告費でゼロから集めるのではなく、他者が既に払い終えた集客（プラットフォームの流入・既存コミュニティ・イベントの群衆）に相乗りする
- **隣接需要（ついで買い）を狙う:** その群衆が「本命の目的のついでに」必要とするもの・あったら買うものは何か。本命そのものではなく、その周辺に金脈がある

**確認する（エージェントが実行できるアクション）:**

| 問い | 具体アクション |
|---|---|
| どこに群衆が既にいるか | 対象領域で「人と金が既に集まっている場所」を最低5つ列挙する（プラットフォーム/マーケットプレイス/大型コミュニティ/定期イベント/流行アプリ）。各々の規模（MAU・出店者数・流通額）を deep-research で裏取り |
| その経済圏で何がついでに売れるか | 選んだ群衆が「本命の目的」のついでに必要とする隣接需要を最低5つ洗い出す。「この人たちは他に何を"ついで"に買うか」を機械的に列挙 |
| ただ乗りできる集客導線はあるか | そのプラットフォームに掲載・出品・出店・連携して、他人の流入をそのまま自分の集客にできる導線が実在するか確認（審査・手数料・規約・アカウント停止リスクも） |
| 隣接商品を低単価で置けるか | 群衆が大きいほど「興味ある一部が低単価で契約する」だけで成立する。想定転換率×流入規模で最低ラインの売上が立つか試算 |

> **なぜ大事か:** 集客はビジネス最大のコスト。ゼロから群衆を作るのは高くつく。**既に他人が集めた群衆に相乗りすれば、集客コストが実質ゼロになり、当てた時に一気に跳ねる。** 原則1で「売れる証拠」を確認しても、集客を自前でゼロから背負うと数字が合わない。この原則は「どこで戦えば集客がタダになるか」を先に選ぶ。

**具体例（この発想の2つの原型）:**

- **リーバイス／ゴールドラッシュ（1848, アメリカ）:** 金を掘りに30万人が殺到した。掘る側の大半は儲からなかったが、「労働者が集まる＝丈夫なズボンが売れる」と読んで作業着（ジーンズ）を売ったリーバイスは大儲けした。**金を掘る側ではなく、掘りに来た群衆に道具を売る側**に回るのが原型。
- **BASE（ECプラットフォーム）:** BASEが流行り出店者・買い手が集まっているのを見て、「ここに集まる人は他に何を"ついで"に買うか」を考え、アクセスの集まるBASEに隣接商品を掲載する。自前で集客せずとも大量アクセスがそのまま流れ込み、興味を持つ一部が低単価で契約する、という設計が成り立つ。**アクセスの集まるところに、儲かるものを投じる。**

**原則1・原則4との接続（"自前集客をしない"背骨）:**

- **原則1（売れる証拠）へ:** 相乗り先＝既に集客データが可視化された場所。原則1.5で場を選んだら、その場の集客データ（PFの流入・競合の順位・流通額）をそのまま原則1の deep-research に渡す。場を先に選ぶと原則1の裏取りが一気にやりやすくなる。
- **原則4（広告依存の脱却）へ:** 原則4は「当たった"後"に広告を減らす」、原則1.5は「最初から広告が要らない場を選ぶ」。同じ『他人の集客に相乗りする』思想を、入口（1.5）と出口（4）の両端に置く。ただし相乗りには税がかかる（規約での締め出し・手数料・アルゴリズム変更で一夜にして流入消失）。プラットフォーム依存は集客を"借りている"状態なので、規約と手数料率を先に読み、原則4の SEO・自前導線への逃げ道を最初から設計する。

> **deep-research 連携:** 「どこに群衆がいるか」「その規模」「ただ乗りできる導線の有無・手数料・規約」は推測せず、deep-research スキルで各プラットフォームのMAU・流通額・出店条件・手数料を引用付きで裏取りしてから市場を選ぶ（＝群衆の実在と規模を客観データで確認する）。

### 原則2. 「1%だけ良くする」ポジショニング

**やること:** ゼロから発明しようとさせない。**既に売れているツールの不満点を1つだけ**特定し、そこだけを潰す差別化軸に絞る。

- 「既存の〇〇（競合名）の、どの1点が不満か」を具体化する
- 大発明は不要。既存の成功を土台に、少しの改善で差別化できる
- 「誰の・どの具体的業務か」に絞るのも1%改善の一種（例: 汎用議事録要約 → 訪問看護の記録特化）

> **なぜ大事か:** 大発明は不要。既存の成功を土台に少し改善するだけで差別化できる。

### 原則3. 「売れるか試してから伸ばす」

**やること:** いきなり完成品を作らせない。次の順で「需要の反応」を先に取る。

1. **MVP**（最小の動くもの。またはランディングページだけ）を最速で作る
2. **小額広告 or 直接ヒアリング**で需要をテスト（想定ユーザー3〜5人に聞く / LPで事前登録を集める）
3. **反応があれば本格投資**。無ければピボット。作り込みはここから

> **なぜ大事か:** 完成品を作ってから「誰も欲しがらなかった」を防ぐ。

**この段階で初めて mvp-development スキルに繋ぐ。** MVPは「削るほど早く形になる」。原則1・2で絞った1点だけを縦に通す。

### 原則4. 当たったら集客を「広告依存」から脱却させる

**やること:** 原則3で需要が確認できた**後**の成長段階で適用。集客を有料広告だけに頼らない構造へ移す。

- **SEO**（検索流入。search-optimization スキルと連携）
- **自動コンテンツ**（ブログ・比較記事・LLMO/GEO）
- **アフィリエイト**（他者に売ってもらう）

> **なぜ大事か:** 広告費を減らしても回る状態を作る。

## 進め方（統合フロー）

```
新規プロダクト相談
  ↓
【原則1】deep-research で市場調査(競合・需要・課金導線) → 5点確認 ── 怪しい → そこが宿題。実装保留
  ↓ 通過
【原則1.5】人と金が既に集まる場を選ぶ(相乗り先) ── 自前ゼロ集客が要る土俵 → 場を選び直す
  ↓ 場が定まる
【原則2】既存の不満1点に絞る（1%改善のポジショニング）
  ↓
【原則3】MVP/LP → 需要テスト → 反応あり ── なし → ピボット（原則1へ戻る）
  ↓ 反応あり
  ここで初めて mvp-development で本実装
  ↓ ローンチ後
【原則4】SEO+自動コンテンツ+アフィリで広告依存を脱却
```

## Red Flags — この応答をしそうになったら止まる

以下は「需要検証を飛ばした」サイン。出そうになったら原則1に戻る。

- いきなり「まず技術スタックは〇〇で」「`create-next-app` から」と実装第一歩を答えている
- 「誰が使う/機能/ゴール」だけ聞いて、**検索ボリューム・競合・課金導線を聞いていない**
- ユーザーが「技術は決めた」と言ったのを理由に、需要検証を省略している
- 機能一覧・データ設計・画面設計の話に入っている（原則3の反応確認より前に）
- 「とりあえず動くものを作りましょう」（＝需要未検証のまま作り込み開始）
- 競合・需要の調査を「ユーザーに調べておいてもらう」で済ませている（＝自分で deep-research を回していない）
- 原則1で市場調査が必要なのに、素の単発 WebSearch を数回叩いただけで終えている（＝deep-research の体系的調査を使っていない）
- 集客を「これから自分でゼロから集める」前提で設計している（＝**既に人と金が集まっている場所＝プラットフォーム/群衆に相乗りする**選択肢＝原則1.5を検討していない）
- 「掘る人（＝儲かっている本業プレイヤー）」側で正面から戦おうとしている（＝混雑した金脈を掘りに行き、"掘る人に道具を売る"隣接ポジションを見ていない）
- プラットフォームに乗る前提なのに、**その規約（出店可否・競合禁止・手数料率・アカウント停止リスク）を読んでいない**

**すべて意味するもの: コードの話を止めて、原則1の5点確認（＋deep-research による市場調査）に戻る。加えて「想定ユーザーが既に集まっている場所はどこか／そこに隣接商品を相乗りで差し込めるか（＋その場のただ乗りコストと規約リスク）」を原則1.5として原則1の調査に含める。**

## よくある合理化と現実

| 合理化 | 現実 |
|---|---|
| 「ユーザーがもう技術を決めてるから設計を進めよう」 | 技術が決まっている＝需要が検証済み、ではない。むしろ需要未検証のまま実装に走る典型。原則1に戻す |
| 「アイデアは良いから作れば売れる」 | 「良いアイデア」は作り手の主観。原則1の"売れる証拠"は客観データ（検索数・競合・課金導線） |
| 「MVPを作ること自体が検証だ」 | MVPは作る手段。検証は"人に聞く/LPで反応を見る"。作る前にできる検証を飛ばさない |
| 「競合がいないから独占できる」 | 競合ゼロは「需要がない」サインかもしれない。まず需要の存在を確認 |
| 「早く作りたいと言われたので実装を優先」 | 早く作りたい人ほど、間違ったものを速く作って時間を失う。5点確認は数十分。手戻りは数週間 |
| 「これは学習用かもしれないから細かい検証は不要」 | 収益・ユーザー獲得が目的なら検証必須。学習目的かは**推測せず本人に確認**してから省略する |
| 「競合や需要はユーザーが調べるべきこと」 | 競合・相場・検索需要は"調べれば分かること"。エージェントが deep-research で自分で調べる。ユーザーに聞くのは"聞かないと分からないこと"（当事者性・どのニッチか）だけ |
| 「WebSearchで軽く調べたから市場調査は十分」 | 単発検索の寄せ集めは抜け・裏取り不足が出る。原則1の市場調査は deep-research で fan-out＋敵対的検証＋引用付き合成を使う |
| 「良い商品なら、自分のサイトに集客して売ればいい」 | 自前のゼロからの集客が最大のコストで、そこで大半が死ぬ。**既に人と金が集まる場所（プラットフォーム/群衆）に相乗りし、その経済圏で"ついでに買われる隣接商品"を投じる**方が集客コストを他人にただ乗りしてゼロ化できる（ゴールドラッシュで儲けたのは金を掘る人でなく、掘る人にジーンズ＝道具を売ったリーバイス側）。原則1.5＝"想定ユーザーが今どこに群れているか"を必ず入れる |
| 「人が集まっているプラットフォームがあるから、そこに出せば勝手に売れる」 | "群衆がいる＝自分の隣接商品が売れる"とは限らない。売れるのは**その群衆が集まった目的に隣接し、"ついで"に必要とされるもの**だけ（金を掘りに来た人にジーンズは売れるが、無関係な商品は売れない）。「この群衆は何のために集まり、ついでに何を買うか」を具体化してから乗る |
| 「プラットフォームにただ乗りすれば集客コストはゼロ」 | ただ乗りには税がかかる。**規約で締め出される（競合出店禁止・アカウント停止）／手数料で利益が消える／表示アルゴリズム変更や値上げで一夜にして流入が消える**。規約と手数料率を先に読み、依存の逃げ道（原則4のSEO・自前導線への移行）を最初から設計する |
| 「まだ人が集まっていない新しい場所を先取りすれば独占できる」 | 群衆が"まだいない"場所は、原則1の「競合ゼロ＝需要なしのサイン」と同じ罠。**人と金が既に流れている実績のある場所を選ぶ**のが原則1.5の要。先取りの賭けは、群衆と金流の存在を確認できてからにする |

## mvp-development との関係
