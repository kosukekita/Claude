# Diagnose

難しいバグのための規律。フェーズを飛ばすのは明示的に正当化できるときだけ。

関連スキル: 根本原因ゲートが必要なら [systematic-debugging]、デバッガ/プロファイラ等の具体ツールは [debugging-wizard]。本スキルはその中核である**フィードバックループの作り方**に特化する。

## フェーズ1 — フィードバックループを作る

**これがスキルの本体。** 他はすべて機械的作業。バグに対する「速く・決定論的で・エージェントが自分で回せる pass/fail シグナル」さえあれば、原因は必ず見つかる（二分探索・仮説検証・計測はすべてそのシグナルを消費するだけ）。それが無ければ、コードをいくら睨んでも解決しない。

ここに不釣り合いなほど労力を割く。**攻めて、創意工夫し、諦めない。**

### 作り方 — おおよそこの順に試す（安いものから）

1. **失敗するテスト** — バグに届く seam（接合点）で。unit / integration / e2e。**Python なら pytest** が第一候補。
2. **curl / HTTP スクリプト** — 起動中の dev サーバーに対して叩く。
3. **CLI 実行** — fixture を入力に与え、stdout を既知の正解スナップショットと diff。
4. **ヘッドレスブラウザ**（Playwright / Puppeteer）— UI を駆動し DOM / console / network を assert。本環境は browser-automation スキル / chrome-devtools-mcp あり。
5. **キャプチャしたトレースを再生** — 実リクエスト / ペイロード / イベントログをディスクに保存し、そのコードパスだけに単独で流す。
6. **使い捨てハーネス** — システムの最小サブセット（1サービス＋依存をモック）を立て、バグのコードパスを 1 関数呼び出しで叩く。
7. **プロパティ / ファズループ** — 「ときどき出力が間違う」系なら 1000 個のランダム入力を回して失敗モードを探す。**numpy/torch を使うなら seed を固定**して決定論にする。
8. **二分探索ハーネス** — 既知の 2 状態（コミット・データセット・バージョン）の間で出たバグは「状態 X で起動→チェック→繰り返し」を自動化し `git bisect run` にかける。
9. **差分ループ** — 同じ入力を旧版 vs 新版（または 2 つの config）に流して出力を diff。**モデル評価なら fixture + メトリクスのスナップショット diff** が有効。
10. **HITL スクリプト**（最後の手段）— 人間がクリックせざるを得ないとき、`scripts/` 配下のテンプレで**人間を構造的に駆動**する。本環境用に2版を同梱:
    - **Windows ネイティブ:** `scripts/hitl-loop.template.ps1`（PowerShell）
    - **Linux / Mac / Git Bash / WSL:** `scripts/hitl-loop.template.sh`（bash）

    どちらもコピーして手順を編集し実行する。キャプチャした値が `KEY=VALUE` 形式で出力され、あなたが解析して取り込む。

正しいフィードバックループを作れた時点で、バグは 90% 直っている。

### ループ自体を磨く

ループを「プロダクト」として扱う。一度ループができたら問う:

- もっと速くできるか？（セットアップをキャッシュ、無関係な init をスキップ、テスト範囲を狭める）
- シグナルをもっと鋭くできるか？（「クラッシュしない」ではなく**その症状そのもの**を assert）
- もっと決定論的にできるか？（時刻を固定、RNG/numpy/torch の seed を固定、ファイルシステムを隔離、ネットワークを凍結）

30 秒で不安定なループはループ無しと大差ない。2 秒で決定論的なループはデバッグの超能力。

### 非決定論的なバグ

目標は「きれいな再現」ではなく**再現率を上げる**こと。トリガーを 100 回ループ、並列化、ストレス付加、タイミング窓を狭める、sleep を注入。50% で出るバグはデバッグ可能、1% は不可能 — デバッグ可能になるまで再現率を上げ続ける。（**医療AIの確率的な学習run・指標の揺れにそのまま効く**）

### どうしてもループが作れないとき

止めて、明示的にそう言う。試したことを列挙する。ユーザーに次を求める: (a) 再現する環境へのアクセス、(b) キャプチャ成果物（HAR・ログダンプ・コアダンプ・タイムスタンプ付き画面録画）、(c) 一時的な本番計測の許可。**ループ無しで仮説立てへ進まない。**

信頼できるループができるまでフェーズ2へ進まない。

## フェーズ2 — 再現

ループを回す。バグが出るのを見る。

確認:

- [ ] ループが**ユーザーの言った**失敗モードを出している — 近くにある別の失敗ではない。違うバグ = 違う修正。
- [ ] 複数回で再現する（非決定論なら、デバッグできる十分な率で再現する）。
- [ ] 正確な症状（エラー文・誤出力・遅い計測値）を記録した — 後のフェーズで修正が本当に効いたか検証するため。

再現するまで次へ進まない。

## フェーズ3 — 仮説

どれかを検証する前に**3〜5 個の順位付き仮説**を出す。1 個だけ出すと最初のもっともらしい案に固着する。

各仮説は**反証可能**であること: その仮説が立てる予測を述べる。

> 形式: 「もし <X> が原因なら、<Y を変える>とバグは消える / <Z を変える>と悪化する」

予測を述べられないならそれは「雰囲気」 — 捨てるか鋭くする。

**検証前に順位付きリストをユーザーに見せる。** ドメイン知識で瞬時に並べ替わることが多い（「#3 に変更を入れたばかり」）し、既に除外済みの仮説を教えてもらえる。安いチェックポイントで時間節約大。ただしブロックしない — ユーザー不在なら自分の順位で進む。

## フェーズ4 — 計測

各プローブはフェーズ3 の特定の予測に対応させる。**一度に変える変数は 1 つ。**

ツールの優先順位:

1. 環境が許すなら**デバッガ / REPL 検査**。ブレークポイント 1 個はログ 10 個に勝る。（→ debugging-wizard）
2. 仮説を区別する**境界**に絞ったログ。
3. 「全部ログして grep」は絶対にしない。

**すべてのデバッグログに一意の接頭辞**を付ける（例 `[DEBUG-a4f2]`）。後始末は 1 回の grep で済む。タグ無しログは生き残る、タグ付きは死ぬ。

**性能ブランチ。** 性能リグレッションでログはたいてい的外れ。代わりに: ベースライン計測（タイミングハーネス・`time.perf_counter()` / `performance.now()`・プロファイラ・クエリプラン）を取ってから二分探索。先に測る、後で直す。

## フェーズ5 — 修正＋回帰テスト

回帰テストを**修正の前に**書く — ただし**正しい seam が存在するときだけ**。

正しい seam とは、テストが**実際のバグのパターンを呼び出し位置で再現**するもの。利用可能な seam が浅すぎる場合（バグは複数 caller が必要なのに単一 caller のテスト、トリガー連鎖を再現できない unit テスト）、そこに回帰テストを書いても偽の安心を生む。

**正しい seam が無ければ、それ自体が発見。** 記録する。コードベースの構造がバグの封じ込めを妨げている。次フェーズへフラグを立てる。

正しい seam があれば:

1. 最小化した再現をその seam での失敗するテストにする。
2. 失敗を見る。
3. 修正を当てる。
4. 成功を見る。
5. 元の（最小化していない）シナリオでフェーズ1 のループを再実行。

→ TDD の規律は既存の [test-driven-development] と整合。

## フェーズ6 — 後始末＋事後分析

完了宣言の前に必須:

- [ ] 元の再現がもう再現しない（フェーズ1 のループを再実行）
- [ ] 回帰テストが通る（または seam が無いことを記録した）
- [ ] すべての `[DEBUG-...]` 計測を除去（接頭辞を grep）
- [ ] 使い捨てプロトタイプを削除（または明確にマークしたデバッグ用の場所へ移動）
- [ ] 正解だった仮説をコミット / PR メッセージに記す — 次のデバッガが学べるように

**そして問う: このバグを何が防げたか？** 答えが構造的変更（良い seam が無い・caller が絡まっている・隠れた結合）を含むなら、具体を添えて改善へ引き渡す。本環境では mattpocock の `/improve-codebase-architecture` は未導入なので、代わりに [finishing-a-development-branch] での仕上げ、恒久的な学びは [cross-agent-memory] へ保存する。推奨は**修正が入った後**に行う — 着手時より今のほうが情報が多い。
