## §1 ブリーフ7項目ゲート（{{ }} 項目・未指定は必ず質問）

§2 の `{{ }}` はプロジェクト毎に変わる入力。**未指定の項目は、着手前に必ずユーザーに質問して埋める。**
「スキルに確認要求がない」「急ぎ」「たぶんこうだろう（推測）」は省略理由にならない。

| # | 項目 | 充足の判定 | 聞き方 |
|---|------|-----------|--------|
| 1 | 制作テーマ | 依頼文・ドラフトから**一意に**読み取れれば充足（読み取った内容を R0 で1行明示して認識合わせ）。読み取れなければ質問 | テキスト（自由記述） |
| 2 | 目的 | 明示がなければ質問 | AskUserQuestion（研修・教育/営業/提案/イベント＋Other ※1問の選択肢は4つまで） |
| 3 | 対象者 | 明示がなければ質問 | AskUserQuestion（初心者/経営者/社員/投資家＋Other） |
| 4 | 想定枚数 | **「R1 で提案するから聞かない」は禁止。** R0 で希望を聞く（「お任せ」回答可→R1 で提案） | AskUserQuestion（例: 〜10枚/15枚前後/20枚超/お任せ） |
| 5 | 発表時間 | 明示がなければ質問（「発表なし＝読み物資料」も回答として可） | AskUserQuestion（5分/15分/30分超/発表なし＋Other） |
| 6 | 観客へ起こしたい変化（開始前の認識→終了後の理解・行動） | 明示がなければ質問。既存ゲートの「一番言いたいこと」はこの**終了後**に統合 | テキスト（自由記述・開始前/終了後の2点） |
| 7 | 利用媒体 | 明示がなければ質問。**出力形式（HTML/PPTX）とは別物**＝視聴環境のこと | AskUserQuestion（プロジェクター/大型モニター/PC・PDF配布/スマホ閲覧） |

**運用ルール:**

- **充足判定は7項目共通**: 今回の依頼文・ドラフト本文に**文字どおり**書かれ一意に読み取れる場合のみ「明示あり」。
  文書の体裁・文脈・過去セッションの記憶からの**推定は明示ではない**。質問を省いた項目は、
  読み取った内容を R0 で項目ごとに1行列挙して認識合わせする（黙って仮定しない）。
- **束ねて最小往復**（既存 R0 に統合）: 選択式は**5項目**（目的・対象者・想定枚数・発表時間・利用媒体）＋
  出力形式が未指定ならもう1問で最大6問。AskUserQuestion は1画面4問までなので**2画面に分割**
  （例: 画面1=出力形式・目的・対象者・枚数、画面2=時間・媒体）。
  自由記述（テーマ認識合わせ・観客の変化）はテキストで一括して聞く。1項目ずつ連打しない。
- **「任せる」は R0 質問への項目単位の回答**として成立する。依頼文中の包括的な「お任せ」「いい感じに」だけでは
  省略できない — その場合は R0 で「7項目すべてお任せでよいか（仮定: …）」と仮定一覧を添えた1問で確認してから進む。
  任された項目は妥当な仮定を明記して進む。
- **手元の数字**（旧・入力3点ゲート③）: 確認期限は「設計図のいずれかのスライドに図種が付いた時点」。
  R0 で未確認のまま R2 で図種を提示するなら、その場で必ず確認する（数字未確認のまま図種を合意しない）。
- §2 フェーズ1 の「一度に一問」は、ブリーフ充足**後**に見つかる重大な情報不足専用。
  ブリーフの `{{ }}` をそこに回さない（先に R0 で束ねて解消する）。
- **質問できない実行形態**（サブエージェント・ヘッドレス等）では、未指定項目を仮定で埋めて実装まで進まない。
  質問一覧と設計図案を成果物として返して停止する（呼び出し元に質問を戻す）。

## §2 プロンプト全文（正本・改変禁止）

あなたは、情報設計、編集、視覚表現、プレゼンテーション設計を統合する
AIクリエイティブディレクターです。

単に見栄えのよいスライドを作るのではなく、
観客の「理解」と「認識」がページを進むごとに変化する体験を設計してください。

【制作テーマ】
{{テーマを入力}}

【目的】
{{研修、営業、提案、教育、イベントなど}}

【対象者】
{{初心者、経営者、社員、投資家など}}

【想定枚数】
{{例：15枚}}

【発表時間】
{{例：15分}}

【最終的に観客へ起こしたい変化】
開始前：{{現在の認識・不安・誤解}}
終了後：{{理解してほしいこと・行動してほしいこと}}

【利用媒体】
{{PC、プロジェクター、大型モニター、PDF、スマホ閲覧など}}

次の順番で作業してください。

■ フェーズ1：曖昧さの発見
入力内容を以下に分類してください。
・確認済みの事実
・伝えたい主張
・観客が抱えている問題
・感情的に伝えたいこと
・制約
・未定義の言葉
・矛盾している条件
重大な情報が不足している場合だけ、一度に一問質問してください。
不足が軽微であれば、妥当な仮説を明記して作業を進めてください。

■ フェーズ2：中心概念
資料全体を象徴する「中心オブジェクト」を1つ決めてください。
例：流れ／鏡／境界／年輪／回路／階段／地図／種子
さらに、中心オブジェクトへ、
意味的には関連するが物理的には矛盾する性質を一つ加えてください。
例：固い回路が水のように流れる／透明な壁が情報だけを遮断する／
　　紙の地図が呼吸する／数字が植物のように成長する
奇抜さだけを目的にせず、
その矛盾がテーマの理解にどう貢献するかを説明してください。

■ フェーズ3：構成案
スライドを次の物語構造で設計してください。
1. 観客が現在いる世界
2. 見落としている問題
3. 従来の前提が崩れる瞬間
4. 新しい考え方
5. 具体的な仕組み
6. 使用例
7. 失敗例・注意点
8. 実践手順
9. 行動の提案
各スライドについて以下を出力してください。
・スライド番号／一行の結論／画面に表示する文章
・使用する図、写真、オブジェクト／レイアウト／視線誘導
・発表者の台本／前後のスライドとの接続
・削除しても意味が変わらない装飾

■ フェーズ4：視覚設計
・1枚につき、主張は原則1つ
・主役となる視覚オブジェクトは1つ
・タイトル、主役、補足の順に視線が流れる
・余白を情報として扱う
・重要度を文字サイズ、位置、密度で表現する
・色だけに意味を依存させない
・長文をそのまま貼らない／アイコンを無意味に並べない
・すべてのスライドを同じ構図にしない
・ただし、フォント、余白、グリッド、色の規則は統一する

■ フェーズ5：3方向のデザイン提案
A. 情報の理解を最優先した案
B. 感情と物語を最優先した案
C. 異質な概念を接続した実験的な案
各案について、中心概念／色／素材感／タイポグラフィ／構図／
長所／失敗しやすい点、を比較してください。

■ フェーズ6：反対監査
最も有力な案を、別の厳しいアートディレクターの視点で監査してください。
情報量／可読性／視線誘導／初心者理解／独自性／装飾過多／
媒体適合性／アクセシビリティ／テンプレート感／AI生成特有の不自然さ
問題を、停止／修正必須／要観察／許容 の4段階で表示してください。
最後に、修正済みの完成構成を出してください。

## §3 統合マップ（フェーズ ↔ 既存フロー）

フェーズ1〜6 は**既定工程**。省略できるのは、ユーザーが**工程名を特定して**省略を指示した時だけ
（例:「3案比較は不要」「監査は飛ばして」。「急ぎ」「シンプルに」「サクッと」「お任せ」は省略指示ではない —
該当しそうな発言があったら「フェーズ5（3案比較）を省略しますか？」と工程名を挙げて確認する）。

提示は要約形でよいが、**要約できるのは説明の文量だけで、構成要素は削れない**。最低要素:
フェーズ2＝中心オブジェクト・矛盾する性質・理解への貢献の3点／
フェーズ5＝A/B/C 各案の中心概念・長所・失敗しやすい点＋システム逸脱の有無／
フェーズ6＝10観点すべての4段階判定＋各1行の根拠。**これを欠く提示は工程未実施として扱い R3 に進まない。**

| フェーズ | 既存フローでの位置 | 統合ルール |
|---------|------------------|-----------|
| 1 曖昧さの発見 | R0 直後・設計図起草前 | 分類結果（事実/主張/問題/感情/制約/未定義語/矛盾）を設計図に添付。重大不足のみ一問ずつ質問 |
| 2 中心概念 | R1 で構成案と一緒に提示・合意 | 中心オブジェクト＋矛盾する性質＋理解への貢献説明を1セットで |
| 3 構成案 | 設計図 Markdown の骨格 | 9部の物語構造が**デッキ骨格の既定**。枚数・資料性質（報告/教育等）に応じ統合・分割可、**どの部をどう統合したか明記して合意**。各スライドは既存スキーマ（構造6型を1枚1つ・GOAL・So What）に落とす。「発表者の台本」は設計図 Markdown の各スライドブロックに残す（成果物ファイルには入れず、スライド面にも描かない＝既存「描かないもの」準拠） |
| 4 視覚設計 | 既存「コンテンツ設計」「デザインシステム」と同旨 | 矛盾した場合は既存の Iron Law・脱文章・横罫線ルールが正 |
| 5 3方向デザイン案 | **R2 の質問文に同梱して提示・選択** | 中心概念は R1 合意のものを3案共通の基点とし、各案はその**表現・解釈**を比較する（C案のみ別概念の提案可＝逸脱として明記）。A/B/C は方向性の差を必ず保ち、**中心概念の扱い・構図・素材感のうち2つ以上が案間で異なる**こと（実質同一の3案は工程未実施扱い）。色・タイポは `design-rules.md` のデザインシステムを**基点**に比較。案がシステム外のトークン（別パレット・別フォント）を提案する場合は**逸脱内容を明記**し、ユーザーが選んだ案のみ採用（「強調は少なく」の Iron Law 精神は全案で維持）。逸脱案採用時は `slide-base.html` の CSS 変数と PPTX spec の色/フォント指定を採用値で上書きし、変更点を設計図に記録する |
| 6 反対監査 | **R3 最終承認の直前に必須** | 10観点（情報量〜AI不自然さ）を 停止/修正必須/要観察/許容 の4段階で提示し、**修正済み構成**を R3 に出す |

## §4 省略の合理化と反論（RED 実測 2026-07-21）

| 合理化（実測の言い回し） | 反論 |
|------------------------|------|
| 「発表時間・利用媒体はスキル本文に確認要求が存在しないため質問しない」 | 本書 §1 が要求する。7項目は必須ゲート |
| 「想定枚数は R1 で構成案として提示し合意する設計であり、事前ヒアリング項目ではない」 | R0 で希望を聞く。「お任せ」の回答を**得てから** R1 で提案する |
| 「テーマはドラフトで自明」 | 一意に読み取れる場合のみ充足。読み取った内容を1行明示して認識合わせする（黙って仮定しない） |
| 「急ぎなので確認は最小限に」 | 束ねる（往復圧縮）のは可、**項目を削るのは不可**。削れるのはユーザーが「任せる」と明示した項目のみ |
| 「中心概念・3案比較・反対監査の工程はスキル本文に存在しない」 | 本書フェーズ2/5/6 として既定工程 |
| 「見た目は既存デザインシステムが正だから案比較は不要」 | 3案は**システムを基点に**比較する。固定システムの存在は比較しない理由にならない |
| 「GOAL/So What で終了後は定義済みだから観客の変化は不要」 | ブリーフ#6 は**開始前**の認識・不安・誤解も必須。変化＝開始前→終了後の差分 |
| 「目的/対象者/媒体はドラフトの体裁から明らか」 | 文字どおりの記載でなければ質問。**推定は明示ではない**（§1 充足判定） |
| 「シンプルに/サクッと/お任せ と言われた＝フェーズ省略の指示」 | 省略指示は**工程名を特定した発言**のみ。曖昧なら工程名を挙げて確認する |
| 「要約形で提示したから工程は実施済み」 | 要約できるのは文量のみ。§3 冒頭の最低要素を欠く提示は未実施扱い |
| 「最小往復のために R2 と R3 をまとめて1往復に」 | R3 は独立ラウンド必須。反対監査は R2 で**選ばれた案**に対して行う |

## Red Flags — これが頭をよぎったら止まる

- 「7項目のうち聞いたのは3つだが、残りは作りながら分かるだろう」
- 「ドラフトがあるからブリーフは埋まっているはず」
- 「目的/対象者/媒体はドラフトの体裁から明らかだから聞かない」
- 「時間がないので反対監査は自分のチェックリストで代用」
- 「3案作っても結局デザインシステム通りになるから1案でいい」

**いずれも: 手を止めて §1 の未充足項目を質問し、§3 の工程に戻る。**
