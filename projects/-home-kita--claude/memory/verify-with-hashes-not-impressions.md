**ファイルの状態を検証・報告するときは、作業の前後で SHA-256 を取って比較する。** 目視・ls・記憶で
「変わっていない」「復元した」と報告しない。

**Why:** 2026-09-03 に同種のミスを1日で2回やり、どちらも Codex の hash 監査で捕まった。
1. `pytest tests` を回した直後に「state/latest.json は mtime 無変更」と報告したが、**実際は
   テストが本番の state を上書きしていた**（`tests/test_pipeline_dry_run.py` → `run_dry_run` →
   `write_state` が本番パスへ直書き）。私は pytest を回す**前**に取った `ls` の結果を、
   回した**後**の状態として報告していた。
2. その後「バックアップから復元した」と報告したが、**バイト一致していなかった**
   （error の一文が欠落し cleaned_at が新しい時刻になっていた）。内容が近いだけで原状復帰ではない。

いずれも Codex が開始時と終了時の hash を突き合わせて発見した。**hash を取らなければ、
2件とも見逃したまま夜間ジョブを迎えていた。**

**How to apply:**
- 触る前に `sha256sum <file>` と `stat -c %y` を記録し、触った後に同じものを取って**並べて示す**。
  「無変更」と書くなら、前後の hash を両方出す（片方だけは根拠にならない）。
- 「復元した」は **hash が元と一致して初めて成立**する。近い内容は復元ではない。
- 他エージェントに検証を頼むときは、**開始時 hash を渡して終了時と突き合わせさせる**と、
  自分では気づけない副作用（テストが本番を壊す等）が出てくる。
- 副作用の疑いがある操作（テスト実行・スクリプト実行）は、**本番ディレクトリで実行する前に
  書き込み先を確認する**。pytest は安全とは限らない（本番パスへ書くテストが実在した）。
