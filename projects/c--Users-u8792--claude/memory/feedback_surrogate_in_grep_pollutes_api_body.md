孤立サロゲート（high surrogate 範囲 U+D800〜U+DBFF、low surrogate U+DC00〜U+DFFF の片割れ）を含む文字を、Grep ツールの正規表現パターンとして渡したり、会話に生のエスケープ表記で出力したりしてはいけない。Grep はパターンを正規表現として解釈し、エスケープ表記を実際の孤立サロゲート文字に変換する。その生の壊れ文字が tool_use 入力として会話コンテキストに焼き付くと、以後そのセッションでターンを送るたびに Claude Code が API リクエストボディ（1行のJSON）を組み立てる際に不正サロゲートになり `400 The request body is not valid JSON: invalid high surrogate in string: line 1 column N` が出続ける。column N は会話が伸びるたびに変わる。

**Why:** 2026-06-14、ユーザーのWindows文字化け調査の流れで「サロゲートを検索しよう」として、サロゲート範囲をリテラルで含む正規表現を Grep に渡してしまった。その結果このセッション自身が汚染源になり、ディスク上の全ファイル（48063個スキャン、本物の孤立サロゲートは0個＝ファイルは全て健全）に問題が無いのに API 400 が再発し続けた。原因は永続ファイルではなく会話コンテキスト（メモリ上の送信ボディ）。フックの Limit-Text やファイル修正では消せず、ユーザーが /clear するまで止まらなかった。自分（アシスタント）が作り込んだ問題だった。

**How to apply:**
1. サロゲート/特定コードポイントを話題にする調査では、エスケープのリテラル表記を会話本文・ツール引数に絶対に書かない。代わりに「U+D800」のように u+ロー数字を使わない安全表記で書く。
2. サロゲート検出・操作のコードは必ずファイルに書いて実行する（インラインのGrepパターンや bash -c の正規表現に直接埋めない）。検出ロジックは ord(c) と 0xD800/0xDBFF/0xDC00/0xDFFF の数値比較で書けばリテラルを書かずに済む。
3. 検出に使った一時スクリプト自体がサロゲートのリテラルを含むなら、実行後すぐ削除する（残すと次回スキャンや注入で再汚染源になる）。
4. 一度コンテキストが汚染されたら復旧は /clear か新セッションのみ。ファイル削除では直らないと早期にユーザーへ伝える。
5. 関連: 文字化け・JSONスキーマ・サロゲートは別レイヤーの別問題 → [[feedback_powershell_hook_utf8_stdout]]（フック側の surrogate-safe 切り詰め Limit-Text は将来のログ注入には有効だが、今回の直接原因ではなかった）。
